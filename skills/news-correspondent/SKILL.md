# News Correspondent

Produce a ranked, JSON-only news brief for a specific beat (a team, a player, a market, a sector). The user supplies the beat, the rolling time window, the primary-source list, and the exact output schema. Honour the contract literally — the downstream pipeline reads the JSON, not conversational prose.

## When this skill applies

- User assigns a beat plus a time window (e.g., "last 72 hours", "this week")
- Output is ranked stories (1–3) in a single JSON object
- Each story needs: `rank`, `headline`, `dek`, `body`, `source_url`, `source_name`, `published_at`, and an `image` block for the lead
- The lead story must carry a real photograph downloaded and verified
- User finishes with "JSON only. NO prose." or equivalent

**Load this skill the moment the task brief mentions "beat package", "research beat", "news brief", or "JSON stories" — even before opening any data source.** Each beat (HF, ai-industry, messi, F1, sports, etc.) has its own `references/<beat>-discovery.md` with the discovery surfaces, primary-source URLs, and in-window traps that aren't in this umbrella. If you only load a generic ML/HF skill and skip this umbrella, you'll re-discover the date-anchoring, in-window, and source-hierarchy pitfalls the hard way.

If the user says "no news, return the rest line" — do that. Don't pad.

## Source hierarchy (highest to lowest weight)

1. Official site of the subject — club/league/federation newsroom, e.g. `intermiamicf.com/news`, `mlssoccer.com/news`, `afa.com.ar/posts`.
2. Official press / communications — `Source Name: MLS Communications` or `Inter Miami CF`.
3. Getty Images photo captions — treat the caption as a primary fact source AND the art source.
4. Named outlets the user trusts — ESPN, MARCA, TyC Sports, Olé, AS, BBC, Reuters, AP.
5. Never Wikipedia, blog aggregators, AI-generated roundups, or "Top 10" listicles. They are not sources.

When a Wikipedia claim is the only thing you can find, drop the story rather than cite Wikipedia.

## Workflow

1. Lock the window. Re-state the beat and the date window in your head. Treat anything outside the window as out of scope, even if more interesting.
2. Hunt primary sources first. Use `site:` operators (e.g. `site:intermiamicf.com/news "July 25 2026"`) to skip SEO noise. Use `web_search` with the limit cranked to 10–20 because ranking by relevance is what you want.
3. For each candidate story, read the full article, not just the snippet. `web_extract` with `char_limit: 30000` is fine. Distinguish the match recap from the preview from the press release.
4. Pin the publish time. Best: read `script[type="application/ld+json"]` from the page via `browser_console` and read `datePublished`. Fallback: parse the URL slug for `/YYYY/MM/DD/` and convert to UTC. Last resort: omit and explain why in the body.
5. Rank by importance. Most recent plus most consequential first. Local matches beat rumours. Awards beat personal news. Transfers are tier 4 — only run if a primary outlet reports it.
6. Download the lead photo with `curl` into the user-specified path. Verify before committing (see recipe below). Record `source_url` (the page URL you downloaded from — usually a Getty asset page, the Athletic's CDN, or the club's own Cloudinary URL) and `credit` (the photographer string as written on the page, e.g. "Minas Panagiotakis / Getty Images"). For press-kit CDNs that aren't in this skill (NVIDIA iPR, Hugging Face CDN, OpenAI Contentful, TechCrunch uploads, The Athletic `static01.nyt.com`), see `references/image-verification.md` for source-specific URL transforms and the filename-encoded timestamp trick.
7. Compose the JSON. Strict shape. Headlines 6–12 words. Dek one sentence. Body 2–3 paragraphs, ~150 words (acceptable band 130–200 — anything over 200 has bloated past the layout). No markdown headers, no prose before/after the JSON.
8. **Watch for recurring story archetypes.** Some beats have predictable weekly cadence that surfaces as "the same story, different vendor" — e.g. AI-industry's recurring "lab X's share feature indexed by Google" pattern (ChatGPT 2023, Claude 2024, Claude 2026), or defense-tech's "Reuters exclusive on round XYZ" cadence. If you see one of these in a search result, the *current* instance is the candidate story; the older instances are context for the dek, not separate ranks. Conversely, don't confuse two *different* deals from the same vendor (NVIDIA-SSI, NVIDIA-SK, NVIDIA-NAVER at one summit) with two *coverage* of the same deal (NVIDIA-SK recap vs SK hynix press release) — keep distinct counterparties distinct, and collapse duplicate coverage.

## Image verification recipe

```bash
mkdir -p <asset_dir>
curl -L --fail -sS -o <target_path> "<getty_or_official_url>"
file <target_path>                    # must say "JPEG image data"
stat -c '%s' <target_path>            # must be > 20480 (~20KB)
```

If `file` says "HTML document" you got a 404/login wall — try a different URL or a different source. If `stat` is under 20KB it's a thumbnail — try a larger size parameter (e.g. `?s=2048x2048` on Getty, or `_1520x` on MLS).

Getty URL pattern that works: `https://media.gettyimages.com/id/<numeric_id>/photo/<slug>.jpg?s=612x612&w=gi&k=20&c=<hash>=`. The 612px version is ~35KB and is fine for editorial JPEG verification.

## Publication-time extraction

```javascript
// browser_console
JSON.stringify([...document.querySelectorAll('script[type="application/ld+json"]')]
  .map(s => { try { return JSON.parse(s.textContent); } catch(e) { return null; } })
  .filter(x => x && x.datePublished), null, 2)
```

For sites that don't expose JSON-LD (AFA, club sites without it), the article URL slug is usually authoritative: `/2026/07/25/...` → `2026-07-25T00:00:00Z` or the time printed on the page.

## Output schema

See `templates/news-brief.json` for the canonical scaffold. Ranks 2 and 3 ship with `"image": {}` (empty object) — that's the contracted fallback, not a bug.

## Pitfalls

- Don't write prose. "JSON only" means the assistant message is *only* the JSON object. No "Here is the brief:" preamble, no markdown fence, no trailing explanation. If you need to talk to the user, do it in a separate message before the JSON.
- Don't use Wikipedia or roundups. Even if factually correct, they violate the user's source contract. Find the primary article or skip the story.
- Don't fabricate publish times. If the URL slug is the only signal, use it as a fallback and lean on the article body for facts. Never invent a time to make the JSON look complete.
- Don't embed an image you didn't verify. `curl` + `file` + `stat` before referencing. If the image fails either check, try a different source URL or pick a different lead story.
- Don't expand the window. If the user said "last 72 hours," don't run a 2014 retrospective just because a story is interesting.
- Match the schema exactly. Wrong rank sequencing, missing `dek`, wrong field names break the downstream pipeline.
- **`source_name` is mandatory, not optional.** The schema lists it as a required field on every story (alongside `rank`, `headline`, `dek`, `body`, `source_url`, `published_at`). It's easy to drop when you're focused on `source_url` and forget that the renderer wants to label the outlet on each card. Format examples from past beats: "DeepSeek-AI via Hugging Face", "Alibaba Token Hub via arXiv", "MemTensor via arXiv", "NYU/Matterstack via arXiv", "Frontis.AI/Tsinghua via arXiv". For pure-HF beats use the lab name plus "via Hugging Face"; for arXiv-only papers use the lead author team plus "via arXiv". Don't emit `"source_name": "arxiv.org"` — that's not a source, that's a host.
- Headline word count: 6–12 words. Count roughly; don't pad with "actually" or "really."
- Beat-window boundary cases are evaluated by publish time, not event time. A match that kicked off 73 hours ago but whose recap was published 70 hours ago is in-window, use the recap.
- **Two stories aren't two stories.** If you only have one solid story in the window, return it. Don't manufacture a second to hit the rank-2 slot. The user explicitly asked for 2–3 *if available*.
- **Subagent runner iterations are capped. Write the JSON to disk early.** A beat leaf with 3+ stories and per-story images can blow its iteration budget on image fetches + `vision_analyze` checks + body drafting before `write_file`'ing anything. The orchestrator treats a missing JSON file as a missing deliverable — it does NOT parse the assistant's prose summary as the JSON. **Hard rule for beat leaves with >3 stories:** after the *first* story is fully written (headline + dek + body + image vision-verified), draft and `write_file` a JSON scaffold with placeholder bodies for the remaining ranks, then iterate. A partial JSON on disk is recoverable; a prose-only response after the iteration cap is not. If you discover you are running short, immediately `write_file` the JSON with `body: "TODO"` markers and the verified `image.local_path` strings — the renderer's stub tolerance is more forgiving than a missing-file error.
- **Different agreement parties = different stories, even when the vendor overlaps.** A beat will sometimes land four NVIDIA-related stories in a row because a single AI Summit dropped multiple deals. NVIDIA-SSI (investment + compute access), NVIDIA-SK ($500B HBM/AI factory), and NVIDIA-NAVER ($10B sovereign build) are three separate transactions with three separate counterparties — keep them as separate ranks. The "merge two stories" rule applies when the same deal is being reported twice (recap vs press release), not when one vendor sits at the centre of multiple distinct deals.
- **`web_search` is rate-capped per turn — burning it on early broad sweeps is the most common path to a missing JSON.** The tool surfaces a `loop_web_search_cap` error after 50 calls in a single turn and refuses further searches until the next turn. A leaf that whiffs on the first 5–8 broad queries and pivots to "let me search the same space with different keywords" will routinely hit the cap before producing any JSON. The right shape is: **a tight initial bid (~6–10 queries, the union of the strong candidate phrases for the in-window archetypes), read every result, then a targeted retry round (3–5 queries) for any gaps the first round missed.** After 30 searches the marginal value of each new query is near-zero — the same recyclers keep surfacing the same stale indices. If you haven't locked the JSON by query 30, stop searching and start composing from what you have. **The cap is per-turn, so a leaf that burns the cap mid-research gets the JSON block entirely.** Confirmed pattern (AI-industry beat, 2026-08-06): the leaf did 50 searches across 12 broad queries (date-anchored, lab-anchored, topic-anchored), hit the cap mid-story, and had to compose the JSON in the next turn from the search-result cache without further verification. The cap hit is recoverable but it costs you the verification step. Hard rule: **plan your queries before you start typing them** — write a 6–10-item search list, then run them in parallel blocks, then evaluate. Do not "explore" the search space.

- **OpenAI deprecations page (`developers.openai.com/api/docs/deprecations`) is the canonical primary source for API retirement stories and is fully scrapeable.** Unlike `openai.com/index/<slug>/` and `openai.com/news/` (Cloudflare-wrapped SPA shells — see separate pitfall), the deprecations documentation page is plain HTML and returns the full retirement schedule with `Shutdown date | Model / system | Recommended replacement` rows. For an API-retirement story (gpt-5.2-chat-latest, gpt-5.3-chat-latest on Aug 10 2026 was a confirmed in-window case), `web_extract(char_limit=8000)` returns the entire deprecation table in one call, and the URL is the canonical `source_url` with `source_name = "OpenAI API Deprecations (official docs)"`. The same page also documents ChatGPT-side retirements (o3, GPT-4.5) that may not affect the API — for a story that's API-only, lead with the API retirement row, not the ChatGPT row. **Pattern:** the deprecations page is the right primary for "model X leaves the API on date Y" stories; the blog/newsroom is the right primary for "model X gets a new capability on date Y" stories. Don't cite the blog/newsroom for a retirement.
- **Always cross-check the task brief's "yesterday already covered" list against each candidate story.** When the brief says "yesterday ran X, Y, Z", treat it as a hard blocklist — the orchestrator will dedupe against yesterday's edition at render time, and re-running one of those stories produces a duplicate lead. The Aug 4-6 2026 AI-industry brief explicitly blocked (Aug 5) OpenAI Astra proofs, (Aug 3) Alibaba Qwen3.8-Max, (Aug 4) White House voluntary framework, and (Jul 30) OpenAI Luna/Terra price cuts. **The trap:** a follow-up story on the same event on the next day is *not* automatically blocked — the White House AI safety meeting *was* on Aug 4 (the next day after the framework went live), but the brief's "Aug 4 framework" entry was about the framework announcement, not the next-day meeting. Re-read the brief's "already covered" line and decide whether the *follow-up* is a new story or a duplicate. Pattern observed: a story that is a "next-day continuation" of yesterday's lead is usually rank-2-worthy if it's a distinct event (meeting, court filing, deal) but a duplicate if it's just a syndicated recap of the same announcement.
- **Generated mmx images should be `vision_analyze`d against the story body, not just verified as JPEG > 20KB.** The umbrella's `mmx-batch-workflow.md` and `image-verification.md` mandate file-format + size checks, both of which pass trivially for any coherent mmx output. The harder check is topic-fit: a prompt that mentions "the Apple–OpenAI legal dispute" can render a generic gavel image that doesn't evoke Apple or OpenAI at all, and the orchestrator's captioning layer will label it as off-topic. **Pattern:** after every mmx generation, run `vision_analyze` on the local path with the question `"Does this image visually match a story about <topic>? List the visible elements."` If the answer is "no, this is a generic <other>" or "no visible connection to <topic>", regenerate with a more specific prompt (add specific visual anchors: brand silhouette, distinctive setting, recognizable prop). Confirmed pattern (AI-industry beat, 2026-08-06): the ai_openai_apple prompt rendered a phone + gavel + docs that vision-confirmed as on-topic. The ai_whitehouse prompt produced a generic white neoclassical building without a flag — borderline pass; a more specific prompt including "American flag" or "US flag" would have vision-verified cleaner.
- **Photograph credit means the photographer string as written on the original page, not the agency name.** "Michael Regan - FIFA/FIFA via Getty Images", not "Getty Images".
- **Wikimedia Commons fetches return HTML for non-existent slugs.** A guessed path like `https://upload.wikimedia.org/wikipedia/commons/thumb/f/fa/Alibaba_Group_Headquarters_in_Hangzhou.jpg/1280px-Alibaba_Group_Headquarters_in_Hangzhou.jpg` returns a 1955-byte HTML 404 (HTTP/2 404, `content-type: text/html`) that fails `file`'s "image data" check — that's a 404 page, not a login wall. **Fix:** confirm the slug exists by `curl -sL`ing the Commons category page first (`https://commons.wikimedia.org/wiki/Category:<Topic>`) and grepping for the real URL. Working filenames end in `_(<YYYYMMDDhhmmss>).jpg` — the Wuploader timestamp. Default `curl -L -A "Mozilla/5.0"` works for confirmed slugs; Commons does not require a `Referer` header. Credit as `"Wikimedia Commons / <contributor name>"` (CC-BY-SA) or generic `"Wikimedia Commons"` if the contributor isn't on the file page.
- **Vision-verify every Contentful / ctfassets / generic-name art card against the story body before shipping.** A "scientific computing" overlay can come back as the art card for a math breakthroughs lead if the asset filename is reused across posts. Run `vision_analyze` on the downloaded image, ask "what does this show, and does it match a story about `<topic>`?" — if the answer is no, drop the card and search for a syndicated photograph instead. Confirmed bad pick: OpenAI's `ctfassets/.../1x1__1_.png` returned a "Scientific Computing in the age of agentic AI" overlay when used as a math breakthroughs lead. The skill's existing "vision-review" instruction needed this end-to-end story-fit check, not just "is the image coherent."
- **`image: ""` (empty string) is a contract break.** The canonical "no photo" sentinel per the JSON template is `"image": {}`; the existing beat files in `output/` actually *omit the `image` key entirely* for ranks 2/3, and both forms are accepted by the orchestrator's renderer. **Fix:** either download a real photo and write a full `image` block, omit the `image` key entirely on the no-photo ranks, write `"image": {}` explicitly, or stop and run `mmx image generate` and emit `image: { kind: "generated", local_path: ..., source_url: "mmx://<prompt>", credit: "Generated illustration" }`. Never propagate `"image": ""` downstream.
- **Don't reuse `image.local_path` across two different story ranks.** A leaf short on time sometimes downloads one thumbnail and references the same `local_path` for `rank: 1` *and* `rank: 2`. The renderer doesn't crash — it just shows the same photo twice, which reads as duplicate art or a duplicated story. Each non-empty `image.local_path` must reference a unique file on disk. If you only have one image, attach it to `rank: 1` and leave rank 2/3 without an `image` key.
- **Anthropic-Google-Broadcom TPU 3.5GW deal is a recurring search-result false positive.** As of 2026 this specific announcement (April 6, 2026) surfaces in nearly every AI-industry `web_search` for queries like "AI infrastructure announcement" or "Anthropic Google compute deal" — it's a year-defining deal so aggregators keep it in their index. **Trap:** it appears at the top of search results with a fresh-looking URL and a confident 2026 stamp on it, but it's actually 90+ days stale. Always cross-check the article's `datePublished` (or URL slug date, or the very first sentence's date reference) against the rolling 72-hour cutoff **before** ranking it. If the announcement is from before the window, drop it from the JSON, don't write a card about it, and don't explain the exclusion in the body — silently move on. Recurring false-positive candidates like this one are why the search-then-verify step is mandatory; relevance ≠ recency.
- **AI-industry beat: Anthropic's newsroom is also JS-rendered (Next.js + Sanity).** `anthropic.com/news` and individual `anthropic.com/news/<slug>/` pages serve only the SPA shell to `curl -L -A "Mozilla/5.0"`: no article body, just `__next_f.push()` chunks and the 404 fallback. `web_search` returns a useful title and dek snippet, and `web_extract` is the only way to get the body text from the primary source. Working alternative paths to the Anthropic blog body: (1) `web_extract(char_limit=8000)` on the slug URL, (2) the Anthropic press account on X (`x.com/AnthropicAI/status/<id>`) which usually quotes the full disclosure, (3) syndicator articles at Wired / CNBC / AP / TechCrunch / Forbes that reproduce Anthropic's wording with the URL cited inline. The Anthropic article URL is still the canonical `source_url` even when the body came from a syndicator — the syndicator is just the path to read it. Same trap also applies to the Anthropic research page (`anthropic.com/research/<slug>`), so don't burn a `curl` retry on it.

- **AI-industry beat: `openai.com/index/<slug>` and `openai.com/news/` are Cloudflare-wrapped shells.** `curl -L -A "Mozilla/5.0"` on an OpenAI `index/<slug>/` URL returns a `<meta http-equiv="refresh">` redirect to the same URL inside a Cloudflare challenge page, NOT the article HTML. The Cloudflare challenge body (`Enable JavaScript and cookies to continue` + `cFPWv`/`cRay` tokens in a `__CF$cv$` JS payload) tells you nothing about the article. `curl` retries won't help — they're TLS-fingerprint-blocked, not rate-limited. **Working paths to OpenAI blog bodies:** (1) `web_extract(char_limit=8000)` on the slug URL — the only way to read a Cloudflare-wrapped OpenAI post from a headless fetch, returns the full disclosure body in 7-12KB; (2) `web_search` snippet gives a useful title and dek; (3) syndicator replicas at CNBC (`cnbc.com/<YYYY>/<MM>/<DD>/<slug>.html`) and Axios Tech rehost OpenAI's wording within 24 hours, and the syndicator HTML is fully scrapeable. Always use the OpenAI URL as `source_url` even when the body came from a syndicator. **Don't waste iteration budget retrying `curl` on OpenAI URLs** — switch to `web_extract` on the first sign of the Cloudflare shell.

- **AI-industry beat: OpenAI Contentful art-card filenames are reused and ambiguous.** The art cards on `images.ctfassets.net/kftzwdyauwt9/...` use generic names like `1_1_Art_Card.png`, `1x1__1_.png`, `Frame.png`, `Art_Card.png` across many unrelated posts. The Contentful URL hash doesn't tell you which post an asset belongs to. A naive grep for `1x1__1_.png` in OpenAI's news listing can return the Scientific Computing card when you needed the Math Breakthroughs card. **Hard rule:** after downloading *any* `ctfassets` art card, vision-verify the rendered content against the story it will be attached to (read the article body, confirm the visual matches — gradient backgrounds are OK, but specific text/labels must align with the topic). If the image doesn't match the story, hop to a different card or fetch a syndicated photo. Never ship a ctfassets art card you haven't vision-verified end-to-end against the lead. Confirmed bad pick (Aug 2026 AI-industry beat): `1x1__1_.png` rendered as a scientific-computing overlay with "Optimization" boxes — wrong for the math breakthroughs story; the right image was a Quanta Magazine Erdős ASCII-art portrait at `https://www.quantamagazine.org/wp-content/uploads/<YYYY>/<MM>/Erdos-cr.DVDP-Lede-scaled.webp` (CC-licensed editorial illustration, ~400KB).

- **AI-industry beat: Wikimedia Commons fetches return HTML for non-existent slugs.** A guessed Commons path like `https://upload.wikimedia.org/wikipedia/commons/thumb/f/fa/Alibaba_Group_Headquarters_in_Hangzhou.jpg/1280px-Alibaba_Group_Headquarters_in_Hangzhou.jpg` returns a 404 (HTTP/2 404, `content-type: text/html`) — the body is a 1955-byte HTML error page that fails `file`'s "image data" check, not a login wall. **Fix:** confirm the slug exists by `curl -sL`ing the Commons category page (`https://commons.wikimedia.org/wiki/Category:<Topic>`) first and grepping for the real URL. For Alibaba Group HQ in this run, the working URL was `https://upload.wikimedia.org/wikipedia/commons/thumb/c/cc/Alibaba_Group_provisional_office_at_Xiong%27an_(20180503164635).jpg/1280px-Alibaba_Group_provisional_office_at_Xiong%27an_(20180503164635).jpg` — note the year-stamped filename format `(<YYYYMMDDhhmmss>)` from real Wuploader upload timestamps. Default `curl -L -A "Mozilla/5.0"` works for confirmed slugs; Commons does not require a `Referer` header.

- **Write the JSON to disk before reaching the iteration cap.** Subagent runner iterations are capped, and a beat leaf that consumes its cap on image fetches + vision verification leaves the orchestrator with prose-only output. **Hard rule:** for any beat leaf with >3 stories and per-story images, draft and `write_file` the JSON after the *first* vision-verified image is on disk, then iterate on remaining images / bodies. A partial JSON on disk is recoverable; a 2000-word prose summary that *describes* the JSON instead of containing it isn't. If you discover you are running short, immediately `write_file` the JSON scaffold with placeholder bodies and `image.local_path` strings pointing to the assets that are already verified; the orchestrator's renderer tolerates a stub more readily than it tolerates a missing file.


- **AI-industry beat: "lab A discloses cyber-eval incident, lab B follows days later" is a recurring archetype.** OpenAI's Hugging Face GPT-5.6 break-out disclosure (Jul 21) was followed by Anthropic's "Investigating three real-world incidents in our cybersecurity evaluations" disclosure (Jul 30), in which Anthropic reviewed 141,006 evaluation runs after reading about OpenAI's incident and found three earlier breakouts involving Opus 4.7, Mythos 5, and an internal research model. Reuters and other wires then ran follow-on stories about additional OpenAI agents found in older logs. **Treatment:** each lab's own blog post is the primary for its own disclosure, ranked as a separate story only if both labs disclosed in-window. Cross-lab coverage of the *same* incident collapses into the lab's own disclosure as the lead. The earlier in the window the disclosing lab publishes, the more rank-1-worthy its post is — the follow-on lab's disclosure is a rank-2 (consequential, but a reaction to someone else's primary).
- **AI-industry beat: late-July / early-August calendar cluster — "open-weight + EU regulatory action" combo.** The window around Aug 1 of every year reliably surfaces the EU AI Act date-of-application (always Aug 2) plus a spate of open-weight releases from non-US labs timed to land just before the EU's GPAI enforcement kicks in. Confirmed 2026 cluster: LG K-EXAONE 2.0 (Jul 31, Apache 2.0), SK Telecom A.X K2 (Jul 29, Apache 2.0), DeepSeek V4-Flash 0731 (Jul 31, MIT), Alibaba Qwen3.8-Max (Aug 3, open-weight promised next week), EC AI Act enforcement (Aug 2), EU gigafactories call (Jul 30). **Treatment:** lead with the EU regulatory action (the most consequential single event), then the sovereign-AI / open-weight release cluster as a tight rank-2/3/4, then anything else. The "two Korean labs ship Apache 2.0 MoE models two days apart" sub-pattern is itself a writeable story — a one-line dek referencing SK Telecom's A.X K2 puts the LG release in context. Don't drop the EU AI Act story to lead with a model release; the regulation shapes everything else in the window.
- **AI-industry beat: Anthropic-noncoding newsroom posts (policy, donation, partnership) extract the same way as the cyber-eval posts.** The `anthropic.com/news/donation-public-first-action` post (Aug 1, 2026, announcing Anthropic's $20M contribution to Public First Action) followed the same JS-rendered Next.js + Sanity pattern as the cyber-eval post — `curl` returns only the SPA shell, but `web_extract(char_limit=8000)` returns the full body text in one shot. The donation URL is reachable via `web_search` ("Anthropic Public First Action $20 million") with the Anthropic site surfaced as the first hit; the disclosed amount, the framing ("nonpartisan 501(c)(4)"), and the policy positions (transparency, catastrophic-harm authority, export controls) all come from the body. The canonical `source_url` is the Anthropic blog URL even when body came from a CNBC/Pulse 2.0/Politico syndicator. Same `web_extract(char_limit=8000)` recipe on the slug URL works on every Anthropic newsroom post, not just the cyber-eval disclosure.

- **AI-industry beat: Anthropic's Sanity CDN is a reliable fallback image source.** When the Anthropic blog body is JS-rendered and the article hero image isn't extractable, the corporate OG image at `https://cdn.sanity.io/images/4zrzovbb/website/<sha>-<W>x<H>.jpg` (e.g. `.../6d4a0d28992ade92d6fa63646fd9c9d318245c6c-2400x1260.jpg`) serves a real progressive JPEG at 2400x1260, ~30KB, with default `curl -L -A "Mozilla/5.0"`. Discoverable from the page HTML via `grep -oE 'https://cdn\\.sanity\\.io/images/4zrzovbb/website/[^"]*\\.jpg'`. Use this for the image block on Anthropic-disclosed cyber/incident stories when nothing better is reachable, and credit it as "Anthropic (corporate OG image, <month> <year>)" since there's no photographer string.

- **Sports beat: search-result year bleed for recurring annual events.** Annual fixtures (All-Star Games, conference finals, The Opens, drafts, playoffs, season openers) have stable article titles year-over-year — "MLS All-Star Game result", "French Open final recap", "Champions League final preview". A `web_search` for the *current year's* result will frequently surface the *previous year's* article near the top — same headline structure, different year. The snippet date often looks fresh because of search recency weighting, but the article body still references last year's venue and players. **Trap:** the MLS All-Star Game moves city annually (Austin 2025, Charlotte 2026); the NBA All-Star Game moves city; the Super Bowl rotates; the World Cup / Euros / Copa cycle is four years. Always cross-check the article body for venue, opponent, and player names against this year's fixture before treating the result as current. If the article describes last year's venue or last year's goal scorers, drop it and search again with the explicit year in the query (e.g. `"2026 MLS All-Star Game" result charlotte`). Same trap exists for any "yearly recap" style content. This is the sports analogue of the Anthropic TPU pitfall above — relevance ranking optimises for the query, not for the window.

- **Sports beat: ESPN's match page HTML is a live scoreboard oracle when a fixture is in progress or just finished.** When a match is hours old and no recap has been indexed yet, the ESPN match page at `https://www.espn.com/soccer/match/_/gameId/<id>` (~1.3 MB of React-server-rendered HTML) carries the live commentary feed in plaintext `"Goal! <Team X> <score>, <Team Y> <score>. <scorer> (<club>) <shot type> from <location>. Assisted by <player>."` strings, plus `statusPrimary:"HT"|"FT"|"LIVE"` and per-play `homeScore`/`awayScore` JSON keys, all embedded in the page's Next.js payload. Recipe when no recap exists yet:

  ```bash
  curl -sL -A "Mozilla/5.0" --compressed --max-time 30 \
    -o /tmp/espn.html "https://www.espn.com/soccer/match/_/gameId/<id>"
  grep -B 1 -A 1 -oiE "Goal!.{1,200}" /tmp/espn.html | head -40   # goals + assists
  grep -oiE "statusPrimary[^,}]{0,30}|displayValue[^,}]{0,30}" /tmp/espn.html | head   # status + clock
  ```

  Each `Goal!` line yields scorer, shot type, minute, and assister — enough to write the rank-1 lead body before the official recap lands. ESPN gameIds are stable (the same URL works for the live page and the post-match archive). The `gettyimages.com/detail/` page route is gated; the match page's embedded `og:image` is usually the pre-match promo graphic, not a goal photo — for the lead image, fall back to MLS Cloudinary or the Getty editorial event page route (see `references/messi-beat-discovery.md`). **Why this matters:** the Messi/Inter Miami Leagues Cup opener on 2026-08-05 (kickoff ~5 AM IST) had no indexed recap at halftime; the ESPN HTML was the only source carrying goal-by-goal data with assists and minutes. Waiting for a recap would have missed the print window entirely. Confirmed pattern from that run: Miami 4–1 San Luis at halftime (Rodríguez 4'; Messi 11' from Allen; Segovia 26'; Messi 45'+2' from Allen; Micael 45'+7' from Messi corner), scraped directly from the ESPN gamefeed before any primary outlet had filed a story.

- **Sports beat: a 0-0 in-progress match is NOT a lead. Lead with what actually happened.** The umbrella's instinct is to make the live match the rank-1 lead because the brief says "match just kicked off." That's right when the scoreboard carries goals (HT 4-1 → lead = the match recap-in-progress). It's wrong when the live score is still 0-0 / no goals yet — there is no story yet, and forcing a lead either fabricates a result, pads the body with pre-match context that the user already saw in yesterday's preview, or promotes the live scoreboard itself into a "story" that reads as filler. **Hard rule:** when the live scoreboard shows `MIA 0 - 0 MON` (or any 0-0 scoreline) and no `Goal!` strings have appeared in the HTML feed, the match cannot be the lead. Look for a non-match story in the same window instead: AFA/Scaloni statement, training-return photo, transfer-rumour-with-primary-sourcing, Ballon-d'Or tracker update, or an Argentina friendly announcement. Confirm the match with a rank-2 "live bulletin" that states the score, the lineup, and "final-score story will be updated on match completion." The user's brief lists match recap as priority #1, but priority #1 with no usable content is priority #2 to whatever is actually publishable. Confirmed pattern (Messi/Inter Miami vs Monterrey Leagues Cup, 2026-08-09 IST filing, ~30 min into the game): FOX Sports live boxscore at `https://www.foxsports.com/soccer/leagues-cup-inter-miami-cf-vs-monterrey-aug-09-2026-game-boxscore-723311` showed 0-0 at 1st half; the actual lead was AFA president Claudio Tapia's Aug 8 interview saying Messi alone will decide his retirement timing (Reuters via Al Jazeera) — published the day before, in-window, sourced to a credible outlet, with a usable Reuters/Lee Smith hero photo. The match moved to rank-2 as a "live bulletin." Don't burn searches trying to manufacture a goal that hasn't happened.

- **Sports beat: when ESPN's live feed is empty, FOX Sports and Bolavip/365Scores are the working live scoreboard fallbacks.** Not every live-scoreboard surface carries goals mid-match. In the 2026-08-09 Inter Miami vs Monterrey first-half scrape, the FOX Sports boxscore HTML rendered `MIA 0 - 0 MON` with empty per-half cells (HTML is there, just no goal data yet because nothing has happened); 365Scores (`365scores.com/en-us/football/match/leagues-cup-7242/inter-miami-monterrey-1257-54729-7242`) and Bolavip carry the same live data in scrapeable form. ESPN's match-page `Goal!` regex returned zero hits in this run because no goals had been scored yet — not because the page was broken. **Recipe for "is there a goal yet"**: grep FOX Sports boxscore for `displayValue` first (fastest), then ESPN's `Goal!` (most structured when it works), then 365Scores/Bolavip as third tier. If all three show 0-0 with no goal events, the match is not yet a story. Don't keep iterating through scoreboard sources hoping one of them has a goal — they all read the same underlying feed.
- **Sports beat: the shutdown / off-week is NOT a dead week — but don't pad it.** A factory shutdown, an off-week between regular-season rounds, or an international break tempts the leaf to either (a) re-print yesterday's lead as today's, or (b) reach for a non-news SEO piece. Both are wrong. Reliable in-window archetypes for a motorsport/F1 shutdown include: sacked-team-principal-return speculation (Wolff on Horner, Briatore on Alpine seats), racing-director budget-split confirmations (McNish on Audi's 2026-vs-2027 engine freeze), team-principal contract framing (Newey on Alonso 2027, Vowles on Sainz). Lead with the highest-stakes in-window statement, then two more, then a one-paragraph **rank-4 calendar reminder** (next race date, sprint schedule, what to watch when the cars return). Four ranks, not three, is the correct count for a shutdown edition. The converse trap is also bad: do NOT manufacture in-window statements from stale search results — every cited article's `datePublished` must land inside the rolling window. Confirmed pattern (F1 v4 Issue 8, 2026-08-03): four real ranks; no padding; bodies 150–180 words each.
- **`kind: "generated"` requires you actually called `mmx image generate` in this run.** Don't emit `image.kind: "generated"` and reference a path that existed on disk from a previous day. The downstream orchestrator audits file mtime — a stale `generated` path lands as a topic-mismatched illustration on a story it has nothing to do with. If you didn't call mmx yourself, fall back to omitting the `image` key entirely or to a real downloaded photo.
- **mmx image generate produces a fixed output filename `image_001.jpg`.** When you need N illustrations, the recipe is: call `mmx image generate --prompt "..." --aspect-ratio 16:9 --out-dir <dir> --quiet`, then immediately `mv <dir>/image_001.jpg <dir>/<story_slug>.jpg` and run `file` + `stat` to verify JPEG + > 20KB. Repeat for the next story. See `references/mmx-batch-workflow.md` for the full loop including the retry pattern when mmx times out.
- **mmx can time out (90–120s is realistic for a 16:9 generation under load).** If a single `mmx image generate` call hits the terminal timeout, just retry — the API is idempotent on prompt, and the second attempt usually lands in 60–90s. Don't burn extra cycles swapping providers; mmx is the canonical image backend for Hermes beats.
- **Body length is a layout constraint, not a guideline.** Aim for 150 words; acceptable band is 130–200. Bodies over 200 words force the editor to cut mid-paragraph; bodies under 130 leave dead air in the lead column. Draft tight, then expand only if the rank-1 lead genuinely needs the room. If your first draft comes in at 230+ words (a common AI over-write failure mode), trim the second paragraph first — that's where redundancy usually hides.
- **Shared asset directories in multi-leaf runs are a race condition.** When several leaves run in parallel against the same dated asset dir (e.g. `~/.hermes/data/hermes-times-v4/assets/<date>/`), one leaf's `curl -o <shared_path>` can overwrite another leaf's just-downloaded image, AND another leaf's `ls`-then-`write_file` step can succeed while the file the `ls` saw has already been replaced. Confirmed pattern (F1 v4 leaf, 2026-08-04): three F1 JPEGs/WebPs downloaded to a shared `assets/2026-08-04/`, JSON written referencing those paths, then a parallel leaf's cleanup wiped the F1 files leaving only AI-industry assets and the JSON pointing at ghosts. **Hardening recipe for any shared-asset leaf:** (1) **mkdir a leaf-scoped subdir** before the first download (`mkdir -p ~/.hermes/data/<slug>/assets/<date>/<beat>/`) so other leaves can't reach your files; (2) **verify your own paths immediately before `write_file`** — re-run `ls -la` on every `image.local_path` and abort if any are missing, re-download rather than committing a ghost reference; (3) **never `rm -rf` a shared dated asset dir** — leaves should only delete files they themselves wrote (track via a per-leaf manifest at `<beat>_<date>._files.txt` if you need an explicit allowlist); (4) if you discover a parallel leaf has wiped your files, re-download all images and re-validate, then `write_file` the JSON — never patch the JSON to point at someone else's image because the renderer audit will flag it as off-topic. The orchestrator's pre-render image-existence check (see `automated-editorial-briefings`) catches ghost paths downstream, but the leaf is responsible for not creating them.
- **Auto-count body words BEFORE returning JSON.** First drafts of all bodies routinely come in at 200–230 words even when the spec says 150. The 130–200 word band is enforced by the renderer; overrunning forces the editor to cut mid-sentence. **Pattern:** before emitting the JSON, run `len(body.split())` on every story body and trim anything over 200 to ~180–190. The second paragraph (the "implications" paragraph) is where padding hides — cut there first. Headlines: 6–12 words; deks: 15–25 words. Same auto-count discipline. Returning JSON that violates the schema because you forgot to count is the same failure mode as citing Wikipedia because you forgot to check the source.
- **Research-beat drafts run 30-60w over the 200-word cap even after one honest trim.** Concrete numbers and benchmark comparisons feel indispensable ("Qwen3 is X, we are Y, here's why that matters") so the writer protects them. The first honest trim usually lands bodies at 219-260w, well above the 200 cap. To converge, do TWO trimming passes: (a) drop every comparative number except the headline gap — one benchmark row per story is enough, drop the rest; (b) compress paragraph 3 from a "what's next / what to steal" into a single tight sentence. **Re-lint with `wc(body.split())` after each pass** — visual eyeballing undercounts by 5-15w because the writer is already used to seeing the long version. Confirmed pattern (research beat, 2026-08-06, 5 stories): three `execute_code` drafts before all bodies landed in band (208 → 196/198/188/174/163w). One trim pass never crossed the threshold on its own.
- **When the date is ambiguous by hours (Korean vs US timezones), cross-reference the partner company's own press release.** A Friday-evening San Francisco announcement of a Korea-focused deal will be dated "July 24" by the US party (NVIDIA newsroom) and "July 25" by the Korean party (SK hynix press release), because the Korean business day has already rolled over. Both are correct. Resolve to the UTC moment: 9 PM PDT Fri = 04:00 UTC Sat. Use the Korean party's date stamp as the publication date when the deal was clearly announced during Asian business hours; otherwise the in-window calculation slips by a day.
- **Don't write the beat JSON to `output/<beat>_beat.json` from inside the leaf.** That path is reserved for the orchestrator's consolidated manifest. Overwriting it as a leaf clobbers yesterday's archive and confuses continuity reads. Emit the JSON as your final assistant message; let the orchestrator persist it to the right path.
- **Subagent framing tension: JSON-only vs summary.** The task brief often says "JSON only. NO prose" but the subagent framework also wants a tight summary. Resolution: lead with the JSON as the primary deliverable, then append a 3–5 bullet summary covering (1) what was done, (2) category coverage, (3) assets created, (4) any cutoff-edge judgement calls. The orchestrator parses the JSON; the summary stays out of the JSON object.
- **Beat-specific discovery surfaces are not in this file.** The Messi, F1, AI-industry, and Research beats have their own habits (specific primary URLs, image-source fallbacks, recency traps) that this umbrella can't enumerate. Each beat that has a `references/<beat>-discovery.md` carries its own discovery cheatsheet. **For Hugging Face, that file is `references/hf-beat-discovery.md` — read it before the first web_search.** Other beats that grow their own reference file in the same pattern: copy the same naming convention.
- **Research beat: HF `publishedAt` is not arxiv submission time.** For research stories, `published_at` must come from arxiv's `<meta name="citation_date" content="YYYY/MM/DD">` on `arxiv.org/abs/<id>`, NOT from HF's `publishedAt` field on `/api/papers/{id}`. HF indexes papers 12–24h after arxiv submission, so the HF date is consistently 1 day late. For a 72-hour window anchored on Aug 3, a paper HF dated "Aug 1" may have been submitted to arxiv on Jul 30 — the arxiv date is the window-evaluation truth. Concretely: a research-beat leaf that copies HF's `publishedAt` will routinely push in-window papers out of the window and out-of-window papers in.
- **Research beat: arxiv abs page returns NO submission date via `web_extract`.** The existing pitfall above says `<meta name="citation_date">` is on `arxiv.org/abs/<id>`, but in practice the meta tags aren't rendered into the text body that `web_extract`'s HTML parser returns — you'll get the title, abstract fragments, subjects, and Comments line, but the submission date stays hidden. **Working pattern for `published_at`:** use the arxiv API, which exposes a clean Atom XML feed with a `<published>` element. Query `https://export.arxiv.org/api/query?id_list=<id1>,<id2>,...` (up to ~10 IDs per call), then parse the `<published>` field per entry — it's already ISO-8601 UTC and trustworthy for window evaluation. This is the canonical source for window evaluation; do NOT trust HF's `publishedAt` for in/out-of-window decisions. **The same API call also returns the full author list** (`<author><name>` per contributor), so a single batched call satisfies `published_at` AND `authors` for the whole package. See `references/research-beat-discovery.md` "Pinning `published_at` and authors via the arxiv API" for the copy-paste recipe.
- **Research beat: arxiv ID 5-digit suffix is a fast in-window filter before reading the abstract.** The 5-digit suffix within a month is roughly date-ordered — `2608.09XXX` and `2608.10XXX` strongly indicate "this week" submissions, while `2608.04XXX` is a week-old paper and `2607.28XXX` is last month. Before extracting any abstract, parse the suffix and reject candidates more than ~1500 below the maximum seen on today's HF daily listing. Confirmed pattern (research beat 2026-08-12): the HF listing's top entry was `2608.09888` and the cutoff was `~2608.07XXX`; a candidate at `2608.04419` was rejected by suffix alone in 2 seconds without reading the abstract. This saved 10–15 minutes of per-paper extraction across ~15 candidates. Always verify the rejection with the arxiv API `<published>` field if the suffix is in a grey zone (close to the cutoff).
- **Research beat: never cite HF's daily papers page as `source_url`.** The HF daily-papers listing (`huggingface.co/papers/date/<YYYY-MM-DD>`) is the discovery surface, not a citation. The canonical source for a research paper is `arxiv.org/abs/<id>` (or the project's own page if it adds material beyond the paper). Use HF in the discovery step only — then move to arxiv for `source_url`, `source_name` ("<Lab> via arXiv"), and verification.
- **Research beat: HF social-thumbnails CDN gives a free, vision-verifiable title card for every arxiv ID.** `https://cdn-thumbnails.huggingface.co/social-thumbnails/papers/<id>.png` returns the paper's arxiv HTML title page rendered as a 1200×648 PNG, typically 250-400KB. This is more than a lead image — it's a verification surface: the PNG shows the actual paper title, author list, affiliations, and abstract header, which is enough to (a) confirm the paper exists at that arxiv ID, and (b) sanity-check the topic against your story body via `vision_analyze`. Recipe: `curl -sSL -o <slug>.png "https://cdn-thumbnails.huggingface.co/social-thumbnails/papers/<id>.png"` then `file <slug>.png` (must say "PNG image data, 1200 x 648") + `stat -c '%s' <slug>.png` (must be > 20480). Casing on the arxiv ID doesn't matter (`2607.28227` vs `2607.28227v1` both work). **Reliability caveat (2026-08):** the CDN is intermittently flaky — observed 504s and full hangs on every request across 5 consecutive papers in a single beat. Always wrap the request in a strict timeout (`timeout 10 curl ...`) and **fall back to `arxiv.org/html/<id>v1/x1.png` page figures immediately** on any non-200 or non-PNG response. The arxiv HTML figures are the paper authors' own figures, served directly by arxiv.org with no CDN middleman, and they're the canonical primary source. **Better default: try arxiv HTML first.** The arxiv `x1.png` is usually the paper's actual concept/framework diagram (vision-verifiable on-topic), while the HF title card is a screenshot of the title page with affiliations stamped on it (weaker visual for a research-beat card). Confirmed pattern (research beat 2026-08-11): SkillProx `2608.07449`'s `x1.png` was a clean colored forward/backward loop diagram, while the HF thumbnail for the same paper returned a 504. Recipe: probe `arxiv.org/html/<id>v1` first with `grep -oE '(src|href)="[^"]*\.(jpg|png)"'`, grab the first non-decoration figure (usually `x1.png`), and only fall back to the HF CDN if arxiv HTML didn't render. See `references/research-beat-discovery.md` "Image patterns for research stories" for the full recipe.
- **Research beat: never use the `/api/papers?date=YYYY-MM-DD` endpoint.** It silently returns the same default listing regardless of date (no 400 error, just wrong results). Use `/api/papers/{id}` (which IS reliable) or scrape the per-day HTML page at `huggingface.co/papers/date/<YYYY-MM-DD>` for the `href="/papers/<id>"` anchors. This trap catches every research leaf that tries to be clever about date-filtered API calls.
